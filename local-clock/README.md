# 로컬 전광판 Clock Reader

노트북/USB 카메라의 선택 영역을 읽어 OBS Web 농구 샷클락과 경기 시계에 반영합니다. Python 프로그램이 이 컴퓨터에서 OCR을 실행하고, 브라우저 화면에서 카메라·영역·세션을 설정합니다. 영상이나 OCR 모델은 웹 배포 서버로 보내지 않습니다.

## 실행

Python 3.10 이상이 필요합니다. 이 프로젝트에서는 macOS ARM64 / Python 3.12에서 검증했습니다.

프로젝트 루트에서:

```bash
pnpm clock:reader
```

또는 `bash local-clock/run.sh`. 공통 표시 코드를 사용하는 `shared/` 폴더도 프로젝트와 함께 유지하세요. 첫 실행은 `local-clock/.venv`에 라이브러리와 패키지에 포함된 ONNX 모델을 설치하므로 인터넷이 필요합니다. 이후 인식은 오프라인으로 동작하며, 배포된 웹 세션 연결에는 네트워크가 필요합니다. 전역 Python 환경은 변경하지 않습니다.

브라우저에서 **http://127.0.0.1:8765** 를 엽니다. Chrome/Safari 등 카메라 권한을 지원하는 브라우저를 권장합니다. Codex 내부 브라우저에서 카메라가 열리지 않으면 일반 브라우저에서 같은 주소를 여세요. 종료는 실행 터미널에서 `Ctrl+C`입니다. 포트 변경: `pnpm clock:reader --port 8766`.

Windows에서는 다음 명령을 사용합니다:

```powershell
py -3 -m venv local-clock/.venv
local-clock\.venv\Scripts\python -m pip install -r local-clock/requirements.txt
local-clock\.venv\Scripts\python local-clock/app.py
```

### macOS에서 `segmentation fault`로 종료되던 문제

OpenCV 5.0의 기본 연결 요소 알고리즘(`LabelingBolelli`)이 카메라 프레임 처리 중 충돌하는 사례를 확인했습니다. 숫자 여백·콜론·소수점 전처리의 세 호출을 모두 명시적인 SAUF 알고리즘으로 변경했습니다. 최신 코드에서 `pnpm clock:reader`로 다시 실행하고 브라우저를 새로고침하세요. 패키지 재설치는 필요하지 않습니다. 추가 네이티브 오류가 발생하면 터미널에 Python 호출 스택도 출력합니다.

## 사용 순서

1. OBS Web 호스트에서 농구 화면과 원격 컨트롤을 열고 공유 링크를 복사합니다. 이 브랜치의 웹 코드가 실행/배포되어 있어야 합니다. 호스트 화면도 계속 열어둡니다.
2. 로컬 화면에서 **카메라 켜기**를 누르고 카메라 권한을 허용합니다. 여러 장치가 있으면 카메라 목록에서 선택합니다.
3. **지정할 영역**에서 샷클락을 선택해 숫자 한 줄을 드래그하고, 게임클락을 선택해 다른 숫자 한 줄을 드래그합니다. 지정된 두 영역을 같은 프레임에서 동시에 읽으며, 한 영역만 지정해도 동작합니다. 콜론/소수점은 포함하고, 점수·팀 이름·다른 시계는 제외합니다. 영역을 백분율 좌표로 입력할 수도 있으며, 마지막 영역은 이 브라우저에 저장됩니다.
4. 공유 링크를 넣고 **세션 연결**을 누릅니다. 세션 ID만 넣었다면 접속할 중계 서버 주소도 입력합니다. 기존 `NEXT_PUBLIC_REMOTE_ORIGIN`이 설정된 경우 그 주소에서 생성된 공유 링크를 사용하세요.
5. 두 시계의 미리보기에서 **확정 인식값**과 **읽은 후보**를 확인합니다. **현재 인식값**은 두 시계 각각의 최신 후보를 항상 표시합니다. 검증 중·범위 초과·동기화 꺼짐에도 후보와 신뢰도, 웹 전송 여부를 볼 수 있습니다. 게임클락 1분 미만은 정수/소수 인식 여부도 표시합니다. 그 아래 **확정 인식값**은 여러 프레임으로 확인한 값이며, **웹 / 미리보기 시계**는 현재 타이머입니다. 인식이 끊기면 현재 후보는 `—`로 바뀌고 마지막 확정값은 유지됩니다. `7:00 → 420초`, `3:43 → 223초`, `50.1 → 50.1초`, `24 → 24초`입니다. 샷클락 기본 동기화 최대치는 60초, 경기 시계는 1200초이며 변경할 수 있습니다. 최대값을 초과한 인식은 후보와 사유에 표시하고, 마지막 확정값을 유지하며 전송을 보류합니다. 예를 들어 샷클락 대상으로 `7:00`을 읽으면 `420초 인식됨 · 최대값 60초 초과`로 안내합니다.
6. **동기화 시작**을 누릅니다. 영역·입력·인식 설정 변경이나 페이지 새로고침은 동기화를 끄므로 확인 후 다시 시작하세요. 중계 재연결은 자동이며 연결 중에 쌓인 결과는 재전송하지 않습니다.

카메라 없이 확인하려면 영상 입력에서 **테스트 전광판**을 선택하고 영상 열기 → 영역 선택을 합니다. `50.1`, `7:00` 등 텍스트를 직접 바꾸거나 **숫자 가리기**로 누락 처리를 확인할 수 있습니다.

## 타이머 우선 자동 보정 (기본)

정수 구간은 첫 확정값에서 **1초마다 1씩 감소하는 웹 타이머를 시작**합니다. 단, 샷클락의 첫 14·24초 관측이나 해당 값으로의 리셋은 정지 상태로 맞추고, 감소가 확인되면 재생합니다. 카메라가 가려지거나 인식에 실패해도 타이머는 계속 진행합니다. 프레임마다 시계를 다시 설정하지 않습니다.

- 최근 1초의 여러 프레임으로 관찰값을 검증합니다. 일반적인 1초 감소는 그대로 두고, 관찰값이 현재 예측값보다 **2초 이상 작을 때** 확인된 값으로 보정합니다.
- 동일한 관찰값이 **1.2초 이상 계속 확인**되면 실제 전광판이 멈춘 것으로 보고 웹 시계도 정지합니다. 가림/인식 공백 자체는 정지 증거가 아닙니다. 감소가 다시 확인되면 자동으로 재개합니다.
- 샷클락은 **0~24초 범위의 리셋/증가**를 4개 프레임으로 확인한 뒤 반영합니다. **14·24초 리셋은 우선 정지**하고, `14 → 13`, `24 → 23` 감소가 확인되면 재생합니다. 정지 중에는 추가 지연을 차감하지 않습니다. 정상 카운트다운의 `15 → 14`는 리셋으로 취급하지 않습니다. 가려진 사이에 14·24로 리셋되어 이미 `13 → 12`로 진행 중이어도 시간에 맞는 감소 흐름이면 복구합니다. 마지막 관찰값보다 작더라도 현재 타이머 예측보다 2초 이상 크면 보정합니다. 샷클락 24초를 넘는 증가나 임의의 새 경기 시간은 **선택 시계 다시 맞추기** 또는 숫자 더블클릭으로 반영합니다.
- **초 경계와 처리·통신 지연은 자동 보정**합니다. 확인된 `24 → 23` 전환의 앞뒤 촬영 시각 사이에서 경계를 추정하고, 여러 경계의 원형 중앙값으로 0~999ms 위상을 계산합니다. 관찰값과 웹 시계가 같은 정수 구간에 있어도 오차가 추정 불확실성보다 크면 기준 시각을 보정합니다(최소 250ms 차이, 2초 이상 간격). 기울기는 정지 0 또는 재생 −1로 고정합니다.
- 초 경계를 아직 보지 못한 최초 값은 위상 0에서 시작하며, 감소 전환이 확인되면 정밀해집니다. 숫자 전환 간격이 너무 길거나 리셋·정지·소수 전환이 있으면 오래된 정수 위상을 버립니다. 소수 구간에서는 별도의 직선 가설로 오프셋을 추정합니다. 화면에 추정 위상과 전환 프레임 간격에서 계산한 불확실성을 표시합니다.
- 웹캠은 `requestVideoFrameCallback`의 촬영 시각이 제공되면 사용하고, 없으면 프레임 표시 시각을 기준으로 합니다. 같은 프레임을 복사해 두 영역에 동일한 시각을 붙입니다. 촬영/표시 이후 추론·검증·전송에 걸린 시간은 실제 경과 시간으로 반영하고, 서버 RTT를 별도로 중복 차감하지 않습니다. [브라우저 프레임 시각 API](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback)
- **추가 영상 지연**은 기본 0초입니다. 폰 카메라/인코더/스트림 내부에서 이미 버퍼링된 지연은 외부 기준 없이 식별할 수 없습니다. 남은 고정 지연을 알고 있다면 여기에 입력합니다(0~3초, 0.05초 단위). 1초를 지정하면 재생 중에만 한 번 앞당깁니다. 자동으로 추정한 초 경계와 추가 지연은 중복 누적되지 않습니다.
- 정지로 판단하면 보정 없이 실제 관찰값으로 맞춥니다. 예: 같은 `20`이 계속 확인되면 웹도 `20`에서 정지합니다.
- **샷클락 5초 이하 카메라 동기화는 기본 꺼짐**입니다. 각 시계 카드의 체크박스로 샷클락 5초 이하 / 게임클락 1분 미만의 자동 동기화를 독립적으로 바꿀 수 있습니다. 게임클락은 기본 켜짐이며 선택은 이 브라우저에 저장됩니다. 토글을 바꿔도 동기화 시작/중지 상태는 유지됩니다. 아래는 샷클락 토글이 꺼졌을 때의 동작입니다. 관측값이 5초 이하이거나 기존 타이머가 5초 이하에 도달하면 숫자 보정·소수값 덮어쓰기·같은 값에 의한 정지 판정을 멈추고 기존 타이머의 재생/정지 상태를 유지합니다. 인식값과 확정값은 계속 표시합니다. 처음 인식한 값이 이미 5초 이하인 경우에도 타이머를 새로 설정하거나 시작하지 않습니다. 14·24초 리셋 또는 여러 프레임으로 검증한 가림 중 리셋(13·12초 등)이 확인되면 다시 동기화합니다. 이 규칙은 모든 동작 모드에 적용됩니다.
- **소수 구간 동기화를 켜면 자동 모드에서 직선 가설을 추적**합니다. 최근 1.5초의 관측점 `(촬영 시각, 남은 초)`에 대해 정지(기울기 0)와 감소(기울기 −1초/초)를 비교합니다. 오차 140ms 이내인 점들의 신뢰도 가중 지지가 70% 이상인 가설에서 가중 중앙값으로 오프셋을 추정합니다. 초기 감소는 최소 3점/320ms, 흔들리는 정지값의 일반 가설은 최소 4점/600ms의 증거가 필요합니다. 소수점 표시의 100ms 구간은 가운데를 추정 위치로 사용하므로 그보다 정확한 촬영 시점을 안다고 가정하지 않습니다.
- **서로 다른 숫자도 같은 감소 가설의 증거로 합칩니다.** 각 관측을 현재 촬영 시각으로 이동시켜 비교하므로 `59.9 → 59.7 → 59.5`는 세 개의 서로 다른 후보가 아니라 같은 직선을 지지하는 3점입니다. `OCR 80%` 같은 개별 이미지 점수와 가설의 지지율을 구분합니다. 기본 단일 프레임 기준 85%에 못 미쳐도 70% 이상인 소수 후보는 바로 버리지 않고 모으며, 최소 5점/600ms, 신뢰도 가중 지지율 85% 이상, 평균 OCR 점수 75% 이상, 중앙 잔차 60ms 이하를 모두 만족해야 채택합니다. 강한 후보만 있는 경우에는 기존의 빠른 판단을 사용합니다. 후보 하한은 설정 기준보다 0.15 낮되 최소 0.65이며, 사용자가 기준을 0.65보다 낮췄다면 그 값을 따릅니다. 정수·카메라 값만 표시 모드는 기존 단일 프레임 기준을 유지합니다.
- **정지·재개 전환은 최근 관측으로 먼저 판단**합니다. 최근 1.5초 안에서 같은 소수값이 3번 이상, 최소 240ms에 걸쳐 확인되면 빠르게 정지합니다(기본 180ms 샘플 간격에서는 약 360ms). 중간 오독이 있어도 해당 구간의 신뢰도 가중 지지가 70% 이상이어야 하며, 확인점 사이가 850ms를 넘으면 새 증거를 모읍니다. 인식 성공 간격이 500ms 정도로 길어져도 세 번의 일치로 정지할 수 있습니다. 확인된 정지값 이후 시간에 맞는 감소가 두 프레임 연속 관측되면 빠르게 재개합니다. 두 값의 감소 속도, 마지막 실제 정지값과의 차이, 최소 0.3초의 총 감소를 함께 검증하므로 단일 오독이나 0.1초 흔들림은 재개 근거가 되지 않습니다. 빠른 재개는 각 관측 간격이 450ms 이내일 때 사용하고, 조건이 불분명하면 일반 직선 가설의 증거를 더 모읍니다. 전환 후에는 이전 상태의 관측점을 제외해 오래된 정지/감소 가설이 다시 끼어들지 않게 합니다.
- 소수 후보는 **직전 및 최근 확정값에서 `경과 시간 + 2초`를 넘게 변하면 배제**합니다. 거절된 값은 다음 후보의 기준으로 쓰지 않습니다. 그 범위 안에 있어도 직선 가설을 지지하지 않는 값은 제외합니다. 최신 관측점도 선택된 직선에 들어맞아야 보정하므로 현재 오독을 과거 직선으로 덮어 확정하지 않습니다.
- 감소 가설이 확인되면 소수 타이머도 가려진 동안 계속 흐릅니다. 관측 공백은 정지 증거가 아니며 850ms를 넘게 보이지 않았으면 새로운 점을 모읍니다. 정지 가설로 바뀌면 촬영·추가 지연 차감 없이 추정 정지값으로 복구합니다. 재생 가설에서는 촬영 이후 경과 시간과 설정한 추가 지연을 한 번만 차감합니다. 위치 보정은 오차가 120ms 또는 추정 불확실성의 두 배를 넘을 때, 최소 400ms 간격으로 수행합니다. 상세 상태에 선택한 가설·지지점 수·추정 오차를 표시합니다.
- 게임클락 토글을 끄면 1분 미만 관측은 기존 타이머를 바꾸지 않고 인식값과 확정값만 표시합니다. 샷클락의 5초 이하 토글도 같은 방식이며 기본 꺼짐입니다. **카메라 값만 표시** 모드에서는 직선으로 자동 재생하지 않고 기존처럼 검증한 실제 관찰값을 표시합니다.

**카메라 값만 표시** 모드는 정수도 자동으로 흐르지 않고 확인된 관찰값만 표시하는 선택지입니다. 웹 세션 없이도 로컬 미리보기를 확인할 수 있습니다. 동기화 중지는 새로운 카메라 보정만 멈추며 이미 실행 중인 웹 타이머를 자동 정지시키지 않습니다. 타이머를 멈추려면 웹에서 정지하세요.

자동 모드를 사용하려면 이번 웹 코드가 배포/실행 중이어야 하고 **OBS 호스트 PC 화면도 새로고침**해야 합니다. 이전 호스트는 카메라 값 표시 기능이 있더라도 자동 재생 기능이 없을 수 있으며, 이 경우 연결 안내에서 새로고침을 요청합니다.

## 인식과 지연

- **RapidOCR 3.9.2 / PP-OCRv6 small / ONNX Runtime CPU**로 선택한 한 줄만 인식합니다. 전체 화면 탐지·방향 분류는 추론에서 생략합니다. [공식 문서](https://rapidai.github.io/RapidOCRDocs/main/install_usage/rapidocr/usage/)
- 자동 모드에는 정면 7세그먼트 LED를 위한 기하학적 보조 인식기가 있습니다. 신뢰도 높은 두 결과가 충돌하면 건너뜁니다. `OCR 모델만` / `7세그먼트만`도 선택할 수 있습니다. 7세그먼트 점수는 확률로 보정된 모델 신뢰도가 아닌 형태 적합도입니다.
- 기본 약 5.5회/초로 **한 프레임씩** 처리합니다. 처리 중 새 프레임은 큐에 쌓지 않습니다. **최근 1초의 관측을 비교**하며 최초 값과 정수 1초 감소는 3개 프레임(최소 240ms), 샷클락 14·24 리셋과 가림 뒤 복구는 4개 프레임(최소 450ms)으로 확인합니다. 매번 1초를 기다리는 방식이 아니라 증거가 충분하면 즉시 확정합니다.
- 정수는 같은 값 또는 1초 감소를 정상 진행으로 처리합니다. 샷클락 자동 모드에서 더 큰 감소는 4개 프레임 확인 후 보정 후보로 넘기고, 실제 보정은 예측값과 2초 이상 차이 날 때만 수행합니다. 샷클락의 0~24초 정수 구간은 증가하거나 1.2초 이상 확정값이 없었던 경우 리셋/복구 후보로 취급합니다. 이때 같은 값뿐 아니라 시간에 맞는 감소 흐름도 4개 프레임(최소 450ms)으로 확인하며, 한두 프레임 오독·빠른 감소·충돌하는 후보는 계속 걸러냅니다. 이 완화는 카메라 값만 표시 모드에도 적용합니다. 24초를 넘는 샷클락 값에는 기존 감소 규칙을 유지합니다. 임의의 새 시작 시간은 **현재 값으로 다시 맞추기**로 기준을 초기화합니다.
- **게임클락 정수 인식은 실제 경과 시간보다 빠른 감소를 차단**합니다. 소수 자동 추적에는 위의 `경과 시간 + 2초`와 직선 가설 검증을 사용합니다. 자동 모드에서도 적용하며, 최근 10초의 확정 흐름을 함께 비교해 작은 급감이 연달아 통과하지 못하게 합니다. 마지막 확정 이후 4초가 지났으면 약 4초 감소까지 허용하고 표시 단위(정수 최대 1초, 소수 0.1초)와 120ms 오차만 더 허용합니다. 가려지거나 정지한 시간에는 감소량이 더 작아도 됩니다. 정확한 `7:00`·`3:00` 리셋은 4개 프레임/최소 450ms 확인 후 새 기준으로 허용합니다. `3:01 → 3:00` 같은 정상 감소는 리셋이 아닙니다. 이 검증은 OCR 채택 단계에만 적용하므로 거절된 후보는 화면에 보이되 웹 타이머에 명령을 보내지 않습니다.
- **게임클락 정지 복구**는 최근 2.2초 안에서 같은 값이 4개 이상 프레임에 걸쳐 최소 1.2초 동안 확인되고, 신뢰도 가중 지지율이 80% 이상일 때 허용합니다. 확인 프레임 사이 850ms 이내의 짧은 가림은 허용합니다. 마지막 확정값보다 최대 10초 큰 값도 정지 상태로 복구하므로, 예측값이 먼저 내려갔거나 약간 낮게 오독했던 경우 자동으로 회복합니다. 복구 증가가 연달아 누적되지 않도록 상한을 유지하며, 실제 경과 시간을 넘는 큰 감소는 계속 차단합니다. 정지 복구에는 재생 지연·위상을 차감하지 않고, 다음 감소가 확인되면 다시 재생합니다.
- **인식값·확정값을 더블클릭**하면 그 숫자를 연결된 웹 호스트에 즉시 수동 전송합니다. 키보드로 숫자에 초점을 맞추고 Enter/Space를 눌러도 됩니다. 자동 동기화가 꺼져 있거나 자동 검증에서 보류된 값, 5초 이하 샷클락도 반영할 수 있습니다. 클릭한 시계만 새 기준으로 설정하며 기존 재생/정지 상태를 유지합니다. 샷클락 `14`·`24`는 정지합니다. 수동 반영에는 촬영·추가 지연 보정을 차감하지 않습니다. 잘못된 형식·설정 최대값 초과·연결 끊김은 오류로 안내합니다. 전송 성공은 웹 호스트로 명령을 보냈다는 뜻이며 실제 OBS 연결은 호스트에서 유지해야 합니다.
- **콜론 뒤 한 자리**는 소수로 읽습니다. `3:9 → 3.9초`, `59:9 → 59.9초`, `3:09 → 3분 9초`입니다. 현재 인식값은 원문을 유지하고 확정값은 소수/분:초 형식으로 표시합니다.
- 소수는 동일 숫자에 투표하지 않고 시간에 맞게 감소하는 관측 경로를 비교합니다(예: `4.9 → 4.7 → 4.5`). 후보 구간에서 신뢰도 가중 지지가 70% 미만이면 보류합니다. 가림·낮은 신뢰도는 투표에 넣지 않고, 오래된 값이나 예측값을 새 촬영값처럼 전송하지 않습니다. 반복 오인식이 정상 시간 흐름과 구분되지 않으면 여전히 오독할 수 있습니다.
- 빈 여백을 먼저 줄여 작은 콜론·소수점이 리사이즈 과정에서 사라지는 것을 줄입니다. 영상에서 구분자가 확인되면 숫자 부분을 나눠 읽고 다시 조합합니다. 같은 숫자열에 구분자만 누락된 OCR 결과는 이 영상 근거로 보완하며, 숫자 자체가 다르면 보류합니다.
- 인식 불가, 후보 하한 미만의 신뢰도, 허용 범위 초과, 오래된 프레임은 건너뜁니다. 소수 자동 모드의 중간 신뢰도 후보는 위의 시간 일치 검증을 추가로 통과해야 합니다. 보이지 않는 콜론·소수점이나 `O→0` 같은 문자를 임의로 만들지 않습니다. **읽은 후보**와 보류 사유를 표시하므로 인식 실패와 범위 초과를 구분할 수 있습니다.
- 로컬 처리 결과가 900ms 이상 오래되면 전송하지 않으며, 웹 호스트는 촬영 후 1초를 초과한 결과·이전 호스트 결과·역순 결과·수동 조작 이전에 찍힌 결과를 버립니다.
- 호스트와 로컬 프로그램의 시계는 왕복 시간으로 맞춥니다. 실행 중인 시계는 촬영~도착 지연만큼 추가 보정합니다. 추가 영상 지연은 선택적인 카메라 버퍼 보정이며 이 짧은 처리·통신 시간과 별개입니다. 정지 관찰값은 정확한 밀리초 값으로 저장하며, 같은 값이 반복되면 다시 쓰지 않습니다. 재생 중에는 표시 단위와 위상 오차를 비교해 불필요한 변경을 막습니다.
- 카메라 원문은 **현재 인식값**에 유지하고, **확정값부터 동기화 전송·웹·OBS 출력·로컬 미리보기 시계**까지 기존 종목별 형식을 사용합니다. 예를 들어 원문 `1:43`은 확정값 `01:43`으로 정규화됩니다. 실제 초 값과 관측 정밀도는 바꾸지 않으므로 `4`를 `4.0`으로 표시해도 소수를 관측한 것으로 오인하지 않습니다. 샷클락은 5초 이상 정수, 5초 미만 소수 한 자리이며, 경기 시계는 1분 이상 `07:00`처럼 두 자리 분:초, 1분 미만 `50.1`처럼 소수 한 자리입니다. 정확히 5초는 `5`, 정확히 1분은 `01:00`입니다. 예를 들어 카메라가 정수 `5`를 마지막으로 읽은 뒤 가려져도 재생 중인 샷클락은 `4.9 → 4.8`로 표시됩니다. 샷클락의 5초 이하 동기화 토글이 꺼져 있으면 실제 소수를 읽더라도 자동 재생을 멈추거나 값을 보정하지 않습니다. 소수 자동 동기화를 켜면 직선 가설에 따라 재생·정지를 판단합니다.
- 웹과 로컬 화면은 `shared/clock-format.mjs`를 함께 사용합니다. 소수 계산 오차로 `16.1`이 `16.2`가 되는 일을 방지합니다. 로컬 화면은 200ms마다 서버 상태를 확인하고, 그 사이에도 재생 중인 타이머를 100ms마다 표시합니다. 정지된 타이머는 자동 감소시키지 않습니다. 일반 글꼴의 곡선을 LED 세그먼트로 오인하지 않도록 세로 세그먼트의 연속 형태도 확인합니다.
- 이 Mac의 **합성 일반 글꼴/7세그먼트 테스트**에서 추론 약 **7~10ms**, 18개 샘플(빈 화면 포함)을 확인했습니다. 180ms 샘플 간격에서 보통 3개 프레임 확인은 약 360ms, 리셋·복구 4개 확인은 약 540ms에 추론·통신 시간이 더해집니다. 실제 카메라·폰 스트림·중계 네트워크까지 1초 이내임을 보장하는 실측은 아직 아닙니다.
- 구분자 분리 인식을 적용한 합성 시간·소수 샘플은 추가 추론을 포함해 약 **20~30ms**였습니다. 넓은 여백, 작은 글자, 흐림, JPEG 압축, 밝은 배경에 대한 실제 모델 회귀 테스트도 포함합니다. 실제 전광판 영상 정확도는 별도 검증이 필요합니다.

실제 촬영은 숫자 높이 최소 40px 정도, 흔들리지 않는 고정 카메라, 가급적 정면 구도를 권장합니다. LED 스캔/셔터에 의한 일부 획 누락, 강한 반사, 심한 원근, 콜론 점멸에는 오독이 남을 수 있습니다. 미리보기에서 원본 색상/대비 강화와 영역을 조절하세요. 샷클락과 게임클락의 영역·필터 이력·정지/재생 판단·위상은 각각 독립적입니다. 선택한 시계의 다시 맞추기는 다른 시계 상태를 지우지 않습니다.

## 폰 카메라 확장

- **폰을 노트북의 웹캠 장치로 연결**하면 같은 카메라 목록에서 선택합니다. 인식과 동기화는 그대로 사용합니다.
- **폰/IP 카메라 스트림** 모드에 직접 MJPEG HTTP(S) 또는 RTSP 주소를 입력할 수 있습니다. OpenCV가 최신 프레임만 보관하며 끊기면 재연결합니다. 일반 카메라 웹사이트 URL, HLS 재생 페이지, 브라우저 전용 WebRTC 사이트는 직접 입력할 수 없습니다.
- 스트림 시간은 로컬 수신/디코딩 기준입니다. 폰/전송 장치가 이미 버퍼링한 지연이나 정지 영상을 새 프레임으로 반복하는 상황은 검출할 수 없으므로 저지연 스트림을 사용해야 합니다. 이 입력 경로는 구현되어 있으나 실제 폰 장비로는 미검증입니다.
- 별도 사이트가 폰 카메라를 중계하는 경우 그 사이트의 WebRTC/미디어 수신 어댑터를 `stream.py` 입력 경계에 붙일 수 있습니다. 이번 버전은 폰 브라우저용 WebRTC 중계 서버까지 만들지는 않습니다.

로컬 서버는 `127.0.0.1`만 수신하며 외부 공개가 필요 없습니다. 브라우저→로컬 요청은 프로세스별 토큰과 동일 출처 검사를 거칩니다. 공유 링크는 기존 원격 컨트롤과 같은 제어 권한이므로 해당 링크를 가진 로컬 프로그램만 세션에 연결하세요. 영상 저장 기능은 없습니다.

## 웹 연동 계약

기존 `/api/remote-ws`를 그대로 사용하므로 추가 OCR 서버나 HTTP 엔드포인트를 배포할 필요가 없습니다. 웹 변경점은 `clockSync.ts`의 `observe` 연산과 `observationVersion: 1`, `trackingVersion: 2`, `decimalTrackingVersion: 1` 기능 표시에 집중되어 있습니다. 기존 수동 리모컨의 프로토콜 버전은 유지합니다.

1. `join` 메시지를 기존 `protocolVersion: 3`, `role: "remote"`, `sessionId`, 임의 `clientId`로 전송합니다.
2. `clock-sync`의 `requestId`에 대응하는 `clock-state.replyTo`로 현재 `epoch`와 호스트 시차를 얻습니다. `observationVersion === 1`인 호스트만 사용합니다. 자동 모드는 추가로 `trackingVersion === 2`를 요구하며, 소수 가설 추적은 `decimalTrackingVersion === 1`인 새 웹 호스트에서만 전송합니다. 운영 웹 배포 후 OBS 호스트 화면도 새로고침해야 합니다.
3. 아래 `clock-command`를 전송합니다. `mode: "run"`은 정수·소수 타이머를 시작하고, `"hold"`는 추정 정지값에서 멈춥니다. `run`의 `offsetMs`는 정수 초 경계 또는 소수 직선의 추정 오프셋과 선택적 추가 지연을 합산합니다. 호스트는 촬영 이후 경과 시간을 별도로 계산합니다. 소수 직선의 현재 위치는 100ms 단위로 올림한 `seconds`와 나머지 `offsetMs`로 전달해 프로토콜의 표시 단위를 유지합니다. `issuedAt`과 `capturedAt`은 반드시 호스트 시차를 반영한 ms 값입니다. `resolutionMs`는 정수/분:초이면 1000, 소수 한 자리이면 100입니다.

```json
{
  "type": "clock-command",
  "command": {
    "id": "unique-frame-uuid",
    "epoch": "host-epoch-from-snapshot",
    "issuedAt": 1234567890500,
    "key": "OBS_BASKETBALL_SHOT_CLOCK",
    "operation": {
      "action": "observe",
      "seconds": 50.1,
      "resolutionMs": 100,
      "format": "seconds",
      "capturedAt": 1234567890450,
      "mode": "hold"
    }
  }
}
```

호스트가 현재 표시값과 비교하여 필요한 경우에만 변경하고 `clock-state`를 방송합니다. 로컬 상태의 전송 수는 수신 확인 수가 아닙니다. 실제 반영 결과는 **웹 시계** 표시로 확인합니다. 과거 호스트나 지연 결과는 무시되며, 원격 저장소의 시계 값을 직접 덮어쓰지 않습니다.

## 검증

**인식 설정 · 상세 상태**에는 확정 전부터 감소·정지 각각의 지지점 수와 가중 지지율을 표시합니다. 이 비율은 OCR 정확도 확률이 아닙니다. 확정값 옆에도 어떤 가설이 몇 점으로 채택되었는지 표시합니다. 가설 채택 후 카메라 관측이 없어도 타이머는 계속 흐릅니다.

로컬 토큰으로 보호된 `GET /api/diagnostics`는 현재 설정에서 처리한 시계별 최근 120개 OCR 결과와 촬영 시각, 보류 사유, 두 가설의 평가 결과를 반환합니다. 이미지·세션 링크를 저장하지 않으며 프로세스 메모리에만 유지하고, 설정/연결 기준을 초기화하면 지웁니다. 실제 카메라에서 발생한 문제를 재현할 때 단일 프레임 점수 부족, 시간 변화 범위 초과, 직선 불일치, 인식 누락을 구분할 수 있습니다.

```bash
pnpm test:clocks
pnpm test:camera
local-clock/.venv/bin/python local-clock/benchmark.py --segments
local-clock/.venv/bin/python local-clock/benchmark.py --image /absolute/path/to/cropped-clock.jpg
pnpm exec tsc --noEmit
```

`test:camera`는 Python 단위 테스트와 실제 OCR 서버→Python WebSocket 클라이언트→프로젝트 중계→호스트 시계 통합 테스트를 실행합니다. 테스트용 세션과 서버만 생성하며 실제 사용자 세션·OBS·카메라는 사용하지 않습니다.
